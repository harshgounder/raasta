## 1_the_product_to_assemble_a_verdict_that_can_be_challenged

### AASIST provides the detector; the wind tunnel provides the demonstration

The AASIST repository is unusually useful for this event because it supplies a research implementation, pretrained models, configurations, and evaluation commands rather than just a paper or a training notebook. Its README reports **0.83% EER and 0.0275 min t-DCF for AASIST**, and **0.99% EER and 0.0309 min t-DCF for AASIST-L**. These are repository-reported benchmark results, not measurements of an assembled website or telephone recordings. Source: `https://github.com/clovaai/aasist`. **Confidence: high.** [1_the_product_to_assemble_a_verdict_that_can_be_challenged[0]] [10]

The case for AASIST-L is practical, not that it is universally superior. Its **85,306 parameters** make it an attractive first hardware experiment, while the documented training configuration for AASIST uses a Tesla V100 and approximately **16 GB RAM**, with batch size **24**. Neither fact proves a specific inference memory requirement. The correct decision is to try a single short-clip inference immediately, before investing in interface integration. Source: `https://github.com/clovaai/aasist`. **Confidence: high for documented specifications; medium for the engineering recommendation.** [1_the_product_to_assemble_a_verdict_that_can_be_challenged[0]] [10]

The proposed interface should have four distinct outputs:

1. **Evidence of synthesis:** the detector's score and thresholded interpretation.
2. **Input quality:** usable speech duration, clipping, silence, and decode status.
3. **Verdict stability:** whether harmless or telephone-like changes alter the result.
4. **Safe next action:** "Call back using a number you already know" rather than "This caller is safe."

These are proposed product decisions. A synthesis detector does not establish a caller's identity or the truth of what they say. The interface should therefore say **"likely synthetic," "no strong synthesis evidence," or "inconclusive"**, not "scammer" and "trusted person."

### The jaw-drop moment is a controlled failure, not a confident animation

A conventional demo uploads a file and displays a red percentage. Your better demo lets the judge drag a **2-10 second selection**, then shows whether the answer survives changing the selection or normalizing loudness. When the result flips, the system visibly refuses to overclaim.

This creates a useful tension: confidence becomes impressive because the audience can challenge it. The idea is a proposed composition of the detector and existing augmentation/evaluation components, not a claim that the listed repositories already deliver this website.

**Decision:** Build an inspectable decision tool, not a fictional universal lie detector. The winning story is "we show when the detector deserves your trust," while retaining genuine-versus-synthetic classification as the central task.

### A benchmark protocol that does not accidentally answer an easier question

Use the official **ASVspoof 2019 LA evaluation split** and the separately collected **In-the-Wild** data requested in the statement. Proposed evaluation design:

- Keep thresholds fixed before external evaluation; do not tune on the final test labels.
- Evaluate **2, 4, 6, and 10 second** crops, with an explicitly documented crop policy.
- Preserve the original recording and create separately labeled stress-test versions.
- Report genuine-speech false alarms, synthetic-speech misses, and inconclusive coverage separately.
- Separate dataset, duration, language where known, and attack family where labels permit.
- Keep augmentation variants from one source recording together; do not count them as independent voices.
- Call window-level scores "window scores," not proven splice boundaries.

These are recommendations, not completed results. No benchmark has been run for the proposed product.
