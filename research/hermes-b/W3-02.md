### An Adversarial Acceptance Matrix For The Live Demo

Everything below is a proposed acceptance test. It is not a statement that the opened repositories have already passed it. **Exact signature, nonce and chain-ID handling for the final assembled stack: CANNOT VERIFY until tested against the pinned account, EntryPoint and SDK versions.**

| Requirement | Owner-visible rule | Attack the demo must attempt | Honest pass condition |
|---|---|---|---|
| Allowed contract | Only the selected merchant/token/router contract. | Same calldata sent to a different contract. | Account rejects the unauthorized target. |
| Allowed function | Only the selected function selector. | Allowed address with a different selector. | Account rejects the unauthorized selector. |
| Per-transaction cap | Each payment must stay under the displayed cap. | One transaction above that cap. | Rejection; splitting rules tested separately. |
| Daily cap | Aggregate authorized spending within a precisely defined period. | Several individually small payments exceeding the aggregate. | Stateful enforcement rejects the excess payment. |
| Recipient allowlist | Only the owner's named beneficiary addresses. | Allowed token contract and transfer function with attacker recipient. | Recipient argument is decoded and rejected. |
| Expiry | Permission expires at the displayed timestamp. | Reuse the agent permission after expiry. | On-chain validation rejects it. |
| Owner exception | A specific otherwise-disallowed payment can be reviewed. | Agent tries to approve itself or broaden its policy. | Only owner authorization permits the exact reviewed action. |
| Nonce / replay | A signed payment should not execute twice. | Submit an already executed authorization again. | Replay rejected by the actual assembled path. |
| Chain binding | Authorization belongs to the intended chain/account. | Replay against another configured chain/account. | Rejection rather than relying on a UI label. |
| Batch accounting | A batch has the same effective constraints as individual calls. | Hide excess spend or another recipient in later batch calls. | Entire batch semantics are checked, or batches are disabled. |
| Token approvals | Spending permissions must not be bypassed through allowances. | Ask the agent to grant an unlimited approval. | Approval is forbidden or separately constrained and explained. |
| Gas exposure | A compromised key must not create unbounded gas liability. | Repeated failed transactions or abusive gas choices. | Defined sponsorship/gas controls and a visible residual-risk limit. |

**Takeaway:** Target and selector checks are necessary but insufficient. The most revealing demo attack uses the *correct token contract and correct transfer function with the wrong recipient*. That distinguishes real argument-level enforcement from an impressive-looking allowlist.

### Case Study: A USD-Style Cap Can Be A Misleading Interface

Suppose the owner sets a proposed demo policy of "5 tokens per payment, 15 per day, only the campus café, expires in ten minutes." The agent receives a hostile webpage telling it to transfer the full balance to an attacker. The important result is not a chatbot warning: it is a signed agent attempt that the wallet rejects, with a receipt linked to the specific rule.

Do not label those limits "$5" and "$15" unless the implementation actually defines valuation and price behavior. A token-unit limit and a fiat-value limit are different policies. Likewise, "daily" must mean a specified reset interval or rolling window; the report has not verified either interpretation for the proposed default composition.

The demo should use a simple transfer path rather than arbitrary swaps. This reduces ambiguity around output assets, slippage, approval side effects and recipient semantics. It also makes the judge's mental model match the tested enforcement surface. This is a design recommendation, not a security certification.

### Case Study: Owner Approval Must Not Become Permanent Permission Inflation

The owner may want to approve one exceptional payment without raising the agent's daily budget forever. A useful interface shows a separate exception card with the exact recipient, amount, token, contract, function, chain and expiry of the proposed action. The owner can execute or authorize that exact action independently of the agent's standing permission.

For the hackathon, the cleanest proposed fallback is **owner executes the exceptional transaction**, rather than inventing a new custom co-signing protocol. Do not claim that the selected permission module automatically implements this inbox. The product wrapper and the selected account's existing owner execution path must be connected and tested.

The residual risk remains important: even a properly constrained stolen key can abuse whatever the owner legitimately allowed. A daily cap bounds the loss; it does not establish that each permitted purchase was sensible, honestly priced or free from merchant fraud.

### Case Study: Why The Stolen-Key Reveal Beats A Chatbot Refusal

A chatbot that says "I cannot do that" leaves the judge wondering whether another prompt would work. The stolen-key reveal changes the question: the attacker no longer needs to persuade the model, because the attacker already has the agent's signing capability. A failed signed transaction then demonstrates a stronger and more understandable boundary.

The website should expose only a disposable test key for a test wallet. Show its allowed scope before revealing it, then let the judge trigger a deliberately excessive payment. This is a proposed interaction design, not permission to publish a production secret or imply that a limited wallet has zero risk.

The next successful small payment is essential. Without it, the audience may conclude the wallet is simply broken. The sequence "valid purchase succeeds, stolen-key theft fails, owner exception succeeds" shows usefulness, restriction and control in one narrative.

## synthesis

The landscape converges on a practical answer: **the wallet boundary is already available in reusable pieces; the complete, tested, judge-friendly product is not established by a repository name.** Choose a narrow transfer scenario, verify its complete policy and turn the results into an understandable live experience.

**Takeaway:** The non-obvious tension is between the most task-shaped code and the most defensible reuse. SingleFee sounds closest to the brief, while established account/module stacks provide clearer component boundaries and, where stated, explicit licenses. Conversely, the simplest recurring-spend implementation is easier to explain but does not necessarily implement the requested ERC-4337 path.

The second tension is between autonomy and safety. More autonomy is not automatically more impressive: a system that can do everything makes it harder to show why the owner remains protected. A tightly constrained assistant that still completes a useful purchase can demonstrate the boundary more convincingly.

The final recommendation is **Path 1 plus the stolen-key, poisoned-page, aggregate-limit and owner-exception sequence**, conditional on real existing modules satisfying the tested policy. If that condition fails, reduce the claim and disclose the missing rule. The winning angle is not "our AI is trustworthy"; it is "you can watch an untrustworthy AI hit a real spending boundary."
